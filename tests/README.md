# Testes do COPO CHEIO

Três camadas, todas rodam no seu computador (ou no GitHub Actions) **sem tocar no banco, no Blob nem no e-mail de verdade**:

| Camada | O que faz | Como roda |
| ------ | --------- | --------- |
| **Unitários** (`unit/`) | Funções puras do projeto: senha, TOTP (2FA), validação de imagem, detecção de IP, URL do site, formatação, normalização dos dados da API, regras do carrinho (escolha do gelo), **o srcset e o endereço das miniaturas, o reaproveitamento dos dados já carregados (a tela só redesenha o que mudou) e o pedido adiantado do cardápio (`public/early.js`: vai só para as páginas do site, nunca para o painel, nunca derruba a página, abre a conexão com o Blob só para o endereço certo e adianta só a foto principal certa de `/` e `/bebidas`: https ou do próprio site, uma versão para celular e outra para computador)**, a **exportação CSV**, o horário com dias especiais, a **medição de visitas** (só com consentimento e sem dado pessoal) e o **sistema de e-mails** (classificação de erros SMTP, assinatura Svix, SPF/DKIM/DMARC, alertas e a compatibilidade dos templates) | `npm run test:unit` (segundos) |
| **API** (`api-test*.mjs`) | A API de verdade (`api/index.ts`) contra um **PostgreSQL local**, com Blob falso, SMTP de mentira e DNS simulado | `npm run test:api` (alguns minutos) |
| **Navegador** (`e2e*.cjs`) | Site e painel num Chromium real (Playwright), de ponta a ponta | `npm run test:e2e` (alguns minutos) |

`npm test` = checagem de tipos + unitários + API. Os de navegador ficam à parte porque precisam do build e do Chromium.

## Preparar (uma vez)

1. **Node 22** ou mais novo e `npm ci` na raiz do projeto.
2. `npm ci --prefix tests` (esbuild, Playwright, driver do Postgres, servidor SMTP de teste).
3. **PostgreSQL 16** escutando em `127.0.0.1:5433`, usuário `postgres`, **sem senha** (`trust`), e o cliente `psql` no PATH.
   Em outro endereço: `TEST_PG_URL=postgres://postgres@127.0.0.1:5433/copocheio_test` e `PGPORT`/`PGHOST` conforme o caso.
   Exemplo com Docker: `docker run -d -p 5433:5432 -e POSTGRES_HOST_AUTH_METHOD=trust postgres:16`.
4. Para os de navegador: `(cd tests && npx playwright install chromium)` e `npm run build` (eles abrem o site já construído).

Os scripts são `bash`. No Windows, use o Git Bash ou o WSL.

## Rodar

```bash
npm run test:unit                 # unitários
npm run test:api                  # todas as suítes de API (cada uma começa de um banco limpo)
bash tests/run-api.sh api-test10  # só uma suíte
npm run build && npm run test:e2e # navegador (todas)
bash tests/run-e2e.sh e2e-track   # só um arquivo
```

Cada suíte imprime `OK: N checks passaram` ou lista o que falhou; o resumo no fim mostra uma linha por suíte e o comando
termina com erro se alguma falhar. A saída completa de cada uma fica em `$TMPDIR/copocheio-tests/<nome>.txt` (ou em `$TEST_OUT`).
`E2E_RETRIES=1 npm run test:e2e` repete uma vez o arquivo de navegador que falhar (o CI usa isso, porque o Chromium em máquina lenta
às vezes perde uma corrida de tempo); o resumo avisa quando precisou da segunda tentativa e guarda a saída da primeira.

## Como funciona

- `server.mjs` empacota `api/index.ts` com o esbuild e serve **site + API** em `127.0.0.1:4180`. O roteamento do `vercel.json`
  (redirecionamentos, reescritas, cabeçalhos) é aplicado com o mesmo pacote que a Vercel usa (`@vercel/routing-utils`).
- `neon-proxy.mjs` faz o driver do Neon falar com o Postgres local; `with-neon-proxy.mjs` roda `scripts/migrate.mjs` e
  `scripts/create-admin.mjs` do mesmo jeito.
- `mailsink.mjs` é o servidor SMTP de mentira (os e-mails enviados ficam acessíveis ao teste, com os cabeçalhos como chegaram; ele também simula recusas
  reais: `451` temporário, `552 5.2.2` caixa cheia, `554 5.7.1` política, endereço inexistente, usuário/senha recusados e queda); `dnsmock.mjs` simula o DNS dos
  domínios de e-mail (MX/A e, para a conferência de SPF/DKIM/DMARC do painel, TXT/CNAME, que os testes mudam por `/__dns`); o Blob é um servidor falso na porta 4181.
  O **provedor de e-mail opcional** (`api-test21`) é um simulador dentro do próprio teste: **nenhum e-mail real, domínio real ou provedor real** é usado.
- `reset.sh` recria o banco `copocheio_test`, aplica **todas** as migrations e cria o owner de teste
  (`dono@copocheio.local` / `senha-forte-123`). `fresh.sh` = `reset.sh` + reinício do servidor. `serve.sh` reinicia só o servidor.

## Medição de desempenho (`tests/perf/`)

Ferramentas para **medir** o site (não são testes que passam ou falham): carga a frio, rolagem do cardápio, interações, memória, saltos de layout (CLS), comparação
de capturas de tela antes/depois e Lighthouse, sempre num celular simulado (CPU mais lenta + 4G lento) e sobre o site de teste. Como usar e como ler os números:
[`tests/perf/README.md`](perf/README.md). O relatório da otimização, com os números de antes e depois, está em [`docs/DESEMPENHO.md`](../docs/DESEMPENHO.md).

## O que estes testes **não** provam

- O comportamento **da Vercel em produção** (cabeçalhos finais, cache da CDN, `includeFiles`, regras de `has` em redirecionamentos e
  reescritas): o `vercel.json` é validado com `@vercel/routing-utils` e um servidor local, não pela Vercel de verdade.
- O **Neon** real (latência, "dormir" sem uso, limites do plano), o **Vercel Blob** real e a **entrega de e-mail** (SPF/DKIM,
  caixa de spam) com um provedor de verdade. Para e-mail há um **procedimento manual** (Gmail e Outlook reais, ler SPF/DKIM/DMARC em "Mostrar original"): [`docs/EMAIL.md`](../docs/EMAIL.md#8-autenticar-o-domínio-e-conferir-de-verdade-spf-dkim-dmarc).
- **A Resend de verdade.** O provedor opcional de e-mail só foi exercitado contra um simulador: o formato exato dos avisos (webhooks) e das mensagens de erro vêm da documentação pública e **não** foram confirmados no serviço real.
  A assinatura dos avisos (Svix) foi conferida com o exemplo oficial da documentação da Svix.
- Safari, Firefox e iOS: os testes de navegador usam Chromium.
- A produção em si: nada aqui acessa `copocheio-nu.vercel.app`.

`npm audit --prefix tests` aponta 2 avisos (`path-to-regexp`, via `@vercel/routing-utils`): as dependências desta pasta só existem
para testar e nunca vão para o site publicado.

Depois de um deploy, confira `GET /api/health`, o painel (*Configurações → Painel → Estado do sistema*) e um pedido de teste
(veja `docs/OPERACAO.md`).

### Login do cliente nos testes

Como o login do cliente tem DOIS passos (senha → código enviado por e-mail → sessão), os testes que precisam de uma conta logada usam:

- API: `loginCustomer(client, { email, password })` (em `tests/lib.mjs`). Faz o primeiro passo, lê o código na caixa simulada do servidor de teste e faz o segundo; se o
  primeiro passo falhar (senha errada, e-mail não confirmado, limite...) devolve a resposta dele, igual ao que o servidor respondeu. `registerVerified` já entra assim.
- Navegador: `finishLogin(page)` e `latestLoginCode(email)` (em `tests/e2e-code.cjs`): na tela "Confirme que é você" digitam o código do e-mail mais recente.
- Sem e-mail configurado (`api-test5-modes`, `e2e-mail-off`) não existe caixa simulada: ali o login com a senha certa responde `503 mail_not_configured`, e é isso que se confere.

Login do **painel** nos testes (também em dois passos: senha → código enviado por e-mail → sessão): `Client.login()` e `loginAdmin(client, { email, password })` (em `tests/lib.mjs`), e, no navegador,
`finishAdminLogin(page)` e `adminLoginViaApi(api, creds)` (em `tests/e2e-code.cjs`). Sem e-mail configurado (`e2e-mail-off`, parte de `api-test5-modes`) o painel só abre com o interruptor de
emergência `ADMIN_EMAIL_CODE=off`, que esses testes ligam de propósito (e `api-test5-modes` confere antes que, sem ele, a senha certa responde `503` e nunca abre sessão).
